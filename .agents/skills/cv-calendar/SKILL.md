# cv-calendar

Guide local calendar setup and prepare reusable setup/publishing scripts, following CV Tailor's agent-configured connection model. SQLite remains the application tracker. Publishing is one-way and manual; this skill does not install a background sync service.

## Resume or configure a connection

1. Read root AGENTS.md, run `cv-tailor --json status`, and retain the actual data directory. Pass `--data-dir PATH` on every later CLI call. Load `preferences get` and inspect `calendar_connections`; leave `tracking_connection` and resume preferences intact.
2. Reuse the chosen provider's nonsecret JSON `config_path` and scripts. If the user did not name a provider and there is more than one saved connection, ask which destination to use. Read only the relevant reference: [Google Calendar](references/google-calendar.md) or [Outlook](references/outlook.md). Verify current official provider guidance when preparing the adapter.
3. Keep scripts and nonsecret configuration under the Git-ignored `.cv-tailor-integrations/`. Configuration records provider, selected calendar ID, explicit data directory, stable workspace UUID, timezone, reminder choices, confirmed event plans, and publishing receipts. Validate its workspace UUID and directory before reuse; never silently repoint a connection at another workspace or calendar.
4. Prepare cross-platform Python setup and publish scripts with a dry-run mode. Reuse available libraries; install a provider library only if needed. Use provider APIs for routine publishing. The user runs interactive authorization in their own terminal and browser. Open the official setup URLs before asking them to obtain values. Never ask for secrets, OAuth codes, or credential JSON in chat.
5. Capture secrets with hidden local prompts through `scripts/integration_env.py`. For OAuth, pass results directly in memory to its `save_env_values`; never print provider token responses or exception payloads. Persist credentials only in the Git-ignored `.env.integrations`, verifying it is untracked and ignored first. Load with `dotenv_values(path, interpolate=False)`. Do not create separate token files or reuse a Sheets token with different scopes.
6. Save the chosen provider and absolute JSON setup path with `preferences set --revision N --input preferences.json`. `calendar_connections` is a replacement list: merge this provider into the latest saved list, preserving the other provider. Each item has a `provider` (`googlecalendar` or `outlook`) and `config_path` (an absolute JSON path, or null before setup). Re-read and merge on a revision conflict. Remembering setup does not prove authorization succeeded or authorize publishing.

## Choose and publish events

- Get application metadata through `applications list` / `applications get ID`, never direct SQLite reads. Use supported CLI updates for application changes. The tracker currently provides `follow_up_date`, not interview appointments or application deadlines. Ask for missing interview/deadline details; save user-confirmed scheduling details in the connection's event plans. Never infer appointments from status, job text, or preparation drafts.
- Each plan has a persistent event UUID, application ID, kind (`interview`, `deadline`, or `follow_up`), title, either an all-day date or explicit start/end instants with timezone, and chosen reminders. Keep the same event UUID when rescheduling; use distinct UUIDs for different interview rounds. Reuse the same plan identity when deliberately publishing it to both providers. Derive date-only follow-ups from the current CLI record on every dry run and publish; clearing/changing the source must appear in the preview.
- Confirm timed-event duration and timezone. Resolve ambiguous/nonexistent daylight-saving times before writing. Date-only deadlines/follow-ups stay all-day unless the user chooses a time. Never invent midnight deadlines or a default interview time. Provider all-day end dates are exclusive. Show the actual reminder behavior, including provider limits, before publishing.
- Publish only agreed event fields: company/role, kind, schedule, reminders, and optionally the job URL or a user-supplied meeting location/link. Profile facts, conversations, application notes, CVs, and document contents are excluded unless explicitly requested. Create personal appointments with no attendees; never invite recruiters, send email, alter an existing employer invitation, or create conference calls as a side effect of connecting.
- Use a stable external identity derived from workspace UUID, application ID, and event UUID, independent of its date. Store provider event ID, identity, and last-published managed-field fingerprint after each successful write. Persist receipts atomically. Use provider identity metadata to reconcile a timeout before retrying creation; retries and reschedules must update the same event.
- A dry run shows the exact provider/calendar, event timezone or all-day dates, reminders, proposed creates/updates, and conflicts without sending application data or creating events. Re-read the application and remote event before a live write. Preserve unowned fields and personal notes. If remotely managed fields changed since the last receipt, stop for reconciliation instead of overwriting them. Use conditional writes where supported. Do not import remote edits into SQLite.
- Review the first publish scope with the user unless already authorized. A request to connect alone authorizes setup, not event creation. For later requested publishes, reuse the approved destination and fields. If an event was deleted remotely, stop and ask before recreating it. Archiving/deleting an application or clearing a date does not silently delete calendar entries; preview cleanup separately. Provider failures leave local applications and event plans usable for retry.
- Disconnect by removing only that provider from the latest `calendar_connections` list through the CLI. `[]` clears both remembered calendar connections. Explain that disconnect leaves existing events and provider authorization intact; revoke authorization or remove events only when requested.

## Verify and report

Test generated adapters with fictional fixtures for repeated publishing, rescheduling, multiple interview rounds, all-day dates, DST/timezones, external edits, deleted events, and timeout recovery. A dry run must not mutate either system. Compile scripts without capturing credentials. Perform only the requested live setup/test/publish, then report what succeeded, the saved script/config paths, and exact rerun commands. Clearly distinguish prepared scripts from verified authorization and published events.
